# DS/ML-часть: «Умный кредитный кабинет предпринимателя»

Модуль `credit_ds` отвечает за всё «интеллектуальное» в кредитном конвейере: понять потребность клиента, подобрать продукт, оценить риск, принять решение, назначить цену и объяснить результат. Работает автономно (без платных API и закрытых данных), запускается в Docker, подключается к основному бэкенду как FastAPI-роутер `/ds/*`.

## 1. Как устроен кредитный процесс в банке и где в нём DS

| Этап процесса | Что происходит в банке | Что делает наш модуль | Файл |
|---|---|---|---|
| 1. Потребность | Клиент понимает, зачем нужны деньги | Разбор свободного текста («печь для пекарни, 2,5 млн, на 3 года») в структуру: цель, сумма, срок, залог, срочность | `llm.py` |
| 2. Подбор продукта | Менеджер подбирает продукт под цель и возможности | Ранжирование продуктов + «предодобрено до X ₽» по каждому | `recommender.py`, `decision.max_affordable` |
| 3. Подача заявки | Клиент заполняет параметры и данные о бизнесе | Валидация, проверка полноты | `decision.decide` (шаг 2) |
| 4. Обогащение | Запросы в ЕГРЮЛ/ЕГРИП, ФНС «Прозрачный бизнес», БКИ, внутренние данные | Моки интеграций, детерминированные по ИНН | `mock_integrations.py` |
| 5. Политика (knock-out) | Жёсткие стоп-факторы до скоринга | Ликвидация, массовый адрес, просрочка >90 дн., крупная налоговая задолженность | `decision.decide` (шаг 1) |
| 6. Скоринг | Оценка вероятности дефолта | PD за 12 мес. + рейтинг A–E + причины (SHAP) | `scoring.py`, `train.py` |
| 7. Кредитное решение | Скоринг ≠ решение: учитываются продукт, сумма, срок, DSCR, залог | Лимиты продукта → контр-оферта → ручной андеррайтинг → отказ | `decision.py` |
| 8. Ценообразование | Ставка = стоимость денег + ожидаемые потери + маржа | `rate = база + фондирование + opex + маржа + спред продукта + PD·LGD` | `decision.price` |
| 9. Предложение / сопровождение | Оферта, документы, выдача (в хакатоне симулируются) | Текст объяснения решения для клиента; персональная лента новостей | `llm.explain_decision`, `news.py` |
| 10. Мониторинг | Контроль качества модели в проде | PSI скора, модельная карточка | `monitoring.py` |

**Ключевая идея (как в слайдах кейса):** скоринг — один из элементов конвейера. Модель выдаёт *риск*, а *решение* принимает отдельная политика. Поэтому исходов пять, а не два:

`APPROVED` · `COUNTER_OFFER` (другая сумма/срок/продукт) · `NEED_INFO` · `MANUAL_REVIEW` (андеррайтер) · `DECLINED`

Каждый исход мапится на статус заявки (`next_status`), чтобы основной бэкенд двигал конечный автомат: `APPROVED/COUNTER → OFFER_READY`, `NEED_INFO → NEED_INFO`, `MANUAL → UNDERWRITER_REVIEW`, `DECLINED → DECLINED`.

## 2. Архитектура

```
 текст клиента ─► [intent: правила (+LLM)] ─► цель/сумма/срок
                                   │
 ИНН ─► [моки ЕГРЮЛ · ФНС · БКИ] ─► обогащённый профиль
                                   │
            ┌──────────────────────┴───────────────┐
            ▼                                      ▼
   [recommender]                             [decision engine]
   продукты + «до X ₽»          knock-out → полнота → PD (CatBoost) →
                                лимиты продукта → контр-оферта → цена
                                                   │
                                  [explain: шаблон (+LLM, с guardrail)]
```

Принцип разделения ответственности: **числа и решения — детерминированный код и табличная модель; LLM — только язык**. Это объяснимо, воспроизводимо, дёшево и аудируемо.

## 3. Модель риска

**Задача:** бинарная классификация, дефолт (90+ дней просрочки) в течение 12 месяцев, на момент заявки.

**Что выбрали и почему**
- **CatBoost (градиентный бустинг), 5 глубина, ≈200 деревьев** — стандарт для табличных кредитных данных; нативно работает с категориями и пропусками (тонкая кредитная история = NaN в БКИ-скоре — это сигнал, а не ошибка).
- **Монотонные ограничения** на 15 признаков (больше долг/просрочек → риск не падает; выше маржа/DSCR/БКИ-скор → риск не растёт). Это требование банковской валидации: модель не может «придумать», что просрочки полезны. Проверяется тестом `test_monotonicity`.
- **Калибровка (Platt)** на отдельной выборке: нужна не только ранжирующая способность, но и *честная вероятность*, потому что PD напрямую входит в цену (`PD·LGD`). Платт вместо изотоники, потому что изотоника даёт «ступеньки» (одинаковая цена у разных клиентов).
- **Baseline — логрегрессия** (аналог скоркарты): эталон для сравнения и запасной вариант.
- **Out-of-time разбиение** (train 55% → early-stopping 15% → калибровка 10% → тест 20% по датам), как в банковской валидации; случайное перемешивание дало бы утечку из будущего.
- **Объяснимость:** SHAP-вклады → 2–3 фактора риска и сильные стороны человеческим языком (`REASONS` в `scoring.py`).

**Результат на отложенном периоде (синтетика)**

| Модель | AUC | Gini | KS |
|---|---|---|---|
| Логрегрессия | 0.873 | 0.745 | 0.590 |
| CatBoost (сырой) | 0.874 | 0.748 | 0.610 |
| CatBoost + калибровка | 0.873 | 0.747 | 0.604 |

**Честно об этих цифрах:** данные синтетические, и вероятность дефолта в генераторе задана почти линейной логитой, поэтому логрегрессия отстаёт от бустинга лишь на сотые. Метрики показывают, что пайплайн корректен и модель восстанавливает заложенные зависимости, но **не** переносятся на реальный портфель. На реальных данных ожидаем больший выигрыш бустинга из-за нелинейностей и взаимодействий; это нужно проверять на валидации. Полная карточка с калибровочной таблицей по децилям — `artifacts/model_card.json`.

## 4. Кредитное решение и ценообразование

1. **Knock-out** (до модели): статус ЕГРЮЛ ≠ действует, массовый адрес, просрочка >90 дн., налоговый долг >5% выручки.
2. **Полнота данных:** нет обязательных полей → `NEED_INFO` со списком недостающего.
3. **PD и рейтинг:** A <2% · B <4% · C <7% · D <12% · E ≥12%.
4. **Проверка условий продукта** (`catalog.py`): диапазоны суммы и срока, возраст бизнеса, залог, **DSCR** ≥ порога, сумма/выручка ≤ лимита, PD ≤ порога автоодобрения. Сумма выше лимита автоматического решения → `MANUAL_REVIEW` (принцип четырёх глаз).
5. **Контр-оферта:** перебор «продукт × сумма (100%…20% запроса) × срок», каждый вариант прогоняется через модель заново (меняются DSCR и доля суммы в выручке → меняется PD). Выбирается вариант, максимально близкий к запросу, с штрафом за смену срока и продукта.
6. **Серая зона:** нет автоматического варианта, PD ≤ порога отказа и сумма ≥ 1 млн → андеррайтер, иначе `DECLINED`.
7. **Цена:** `ставка = база + фондирование + opex + маржа + спред продукта + PD·LGD`; `LGD = 0.65 − 0.45·покрытие залогом` (в диапазоне 0.20–0.65). Ставка растёт с риском, залог её снижает.

Каждый ответ содержит `trace` (какие шаги сработали и с какими значениями) — это журнал для аудита и демонстрации жюри. Все пороги и ставки условные и лежат в `catalog.py` и `config.py`.

## 5. LLM: что используем и обоснование

**Ограничение:** open weights, не более 120 млрд параметров, система должна быстро обслуживать много пользователей.

**Архитектурное решение.** LLM не участвует ни в скоринге, ни в решении, ни в расчёте ставки. Он нужен в двух точках:

1. **Intent extraction** — текст клиента → JSON (цель, сумма, срок, залог, срочность). Вывод валидируется `pydantic`; числа, которые нашёл регулярный парсер, *имеют приоритет* над LLM (детерминированное извлечение сумм надёжнее).
2. **Объяснение решения** — переписывание уже готового структурированного решения простым языком. Guardrail: все числа в ответе должны быть подмножеством чисел из входных фактов, иначе используется шаблон.

Оба шага имеют **детерминированный fallback** (правила и шаблоны). Без LLM система полностью работоспособна: это важно для «запуска на обычном ПК» и для отказоустойчивости (таймаут LLM 6 с → fallback).

**Выбор модели (ступенчатый).**

| Профиль | Модель (open weights) | Почему |
|---|---|---|
| Демо на ПК жюри, CPU/слабая GPU | компактная инструктивная модель 4–8 млрд параметров (например, семейство Qwen3-4B/8B, квантованная, через Ollama/llama.cpp) | Задачи узкие (извлечение полей, пересказ 3–4 предложений), хватает малой модели; хорошо работает на русском; влезает в обычное железо |
| Бесплатный внешний сервер / прод | MoE-модель с малым числом активных параметров (класс 20–30 млрд общих параметров) через vLLM | Качество выше при скорости малой модели, т.к. на токен активна лишь часть весов |
| Верхняя граница по ограничению | MoE ~117 млрд общих параметров (класс gpt-oss-120b) | Укладывается в лимит 120 млрд, но для наших задач избыточна: платим латентностью и железом за качество, которое не нужно |

Перед фиксацией в README проверьте актуальные model cards: размер, лицензия (нужна разрешающая, например Apache-2.0) и тег для Ollama/vLLM. Я выбирал по знаниям, и точные версии могли измениться.

**Почему не большая модель для всего:** у нас узкая структурная задача, а ограничение «быстро и много пользователей» диктует минимальную достаточную модель. Основная нагрузка (скоринг и решение) обходится без LLM: на 1000 кандидатов предсказание PD заняло порядка 4 мс, полный `assess` по одной заявке в моём прогоне занимал десятки миллисекунд. LLM-вызовы выносятся на края: кэшируются (`lru_cache` по хешу решения), ограничены `max_tokens`, `temperature=0`, и их можно масштабировать независимо (vLLM с continuous batching). Для продакшена добавить очередь и лимиты на пользователя.

## 6. Рекомендации продуктов и новостная лента

- **Рекомендации:** `score = 0.45·совпадение цели + 0.20·попадание суммы в диапазон + 0.10·срок + 0.25·доступность (предодобренная сумма / запрошенная)`. Продукты, которые клиенту не подходят по возрасту бизнеса или залогу, отсекаются. Для каждого возвращается «предодобрено до X ₽» и ориентировочная ставка: клиент сразу видит реальные возможности, а не абстрактный каталог.
- **Лента новостей** (требование слайда 7): content-based ранжирование. Теги клиента строятся из отрасли, цели, исхода заявки и рейтинга; `score = 0.5·IDF-пересечение тегов + 0.25·совпадение стадии заявки + 0.15·отрасль + 0.10·свежесть`. У каждой новости есть поле `why`: показано, потому что… Лента меняется при смене стадии: после отказа появляются материалы про кредитную историю, при `NEED_INFO` про документы (`test_news_changes_with_context`).

## 7. Синтетические данные

`synth.py` строит заявки МСП: скрытое «качество бизнеса» порождает коррелированные признаки (маржа, просрочки, БКИ-скор, обороты), дефолт моделируется как Bernoulli от логиты с ненаблюдаемым шумом, средний уровень дефолта калибруется на ≈7%. Есть тонкие кредитные истории (NaN), разные формы собственности, отрасли и цели. Фикстуры в `mock_integrations.py` задают демо-сценарии end-to-end:

| ИНН | Сценарий | Ожидаемый результат (из моего прогона) |
|---|---|---|
| 7700000001 | Надёжный клиент | APPROVED, рейтинг A |
| 7700000002 | Тонкая кредитная история | APPROVED, рейтинг B |
| 7700000003 | Перегруженный долгами | DECLINED, рейтинг E |
| 7700000004 | Компания ликвидируется | DECLINED (knock-out) |
| 7700000005 | Серая зона | MANUAL_REVIEW, рейтинг D |
| 7700000006 | Налоговая задолженность | DECLINED (knock-out) |

## 8. Запуск

```bash
pip install -r requirements.txt
python -m credit_ds.train                 # обучение, артефакты в ./artifacts (≈ 1 минута)
python -m pytest -q tests                 # 13 тестов
uvicorn credit_ds.api:app --port 8001     # Swagger: http://localhost:8001/docs

# Docker (модель обучается при сборке)
docker build -t credit-ds . && docker run -p 8001:8001 credit-ds
# с локальной LLM
docker compose -f docker-compose.llm.yml up -d
docker compose -f docker-compose.llm.yml exec llm ollama pull qwen3:4b
```

Переменные окружения: `LLM_BASE_URL` (пусто = без LLM), `LLM_MODEL`, `LLM_TIMEOUT`, `DS_BASE_RATE`, `DS_ARTIFACTS`.

**Эндпоинты:** `POST /ds/intent`, `POST /ds/recommend`, `POST /ds/assess`, `POST /ds/news`, `GET /ds/model-card`, `GET /health`.

```bash
curl -X POST localhost:8001/ds/recommend -H 'content-type: application/json' \
  -d '{"company":{"inn":"7700000001"},"text":"Хочу купить печь для пекарни за 2,5 млн на 3 года"}'
curl -X POST localhost:8001/ds/assess -H 'content-type: application/json' \
  -d '{"inn":"7700000005","requested_amount":2000000,"term_months":36}'
```

## 9. Ограничения и развитие (для раздела «потенциал развития»)

- Метрики синтетические; на реальных данных нужны: out-of-time валидация, стресс-тесты, проверка стабильности по сегментам.
- DSCR считается упрощённо (EBITDA-подобная маржа, фиксированная ставка 20% в признаках, грубая оценка обслуживания текущего долга); в проде заменяется на реальные графики платежей.
- Нет reject inference (модель видела бы только одобренных); в проде нужен.
- Пороги и спреды условные, в банке их задаёт кредитный комитет.
- Развитие: champion/challenger, автоматический ретрейн по PSI >0.25, feature store (Airflow), распознавание документов (OCR + LLM) для сокращения повторного ввода, оптимизация цены по эластичности спроса, fairness-аудит.
